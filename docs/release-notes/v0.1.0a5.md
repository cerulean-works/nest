## Install

```bash
uv add "nest @ git+https://github.com/cerulean-works/nest@v0.1.0a5"
```

or `pip install "git+https://github.com/cerulean-works/nest.git@v0.1.0a5"`. `@main`
remains the development and Early Access path. See
[Install Nest](https://docs.cerulean.works/nest/v0.1.0a5/guide/installation#releases-and-main).

**Compatibility:** keep the SDK at or after the commit the Controller was deployed
from. This release works with a Controller deployed from the tagged commit or an
earlier commit that already has session authentication. If the operator deploys a
newer `main`, use `@main`.

## Why earlier tags do not work with an authenticated Controller

`v0.1.0a1` to `v0.1.0a4` predate session authentication (#20, #25, #32, #38). An
SDK installed from one of them has no `nest` command, cannot sign in, and sends
only `x-nest-request-id` with each call, so an authenticated Controller answers
`UNAUTHENTICATED`. `v0.1.0a5` is the first tag that can sign in. Users on an older
tag must reinstall from `v0.1.0a5` or `@main`; there is no in-place upgrade of a
session.

## Highlights since v0.1.0a4

### SDK and command line

- **Sign-in and sessions** (#20, #25, #32, #69, #68): Google sign-in with PKCE and
  OIDC verification, browser-approved CLI sessions with `nest login`, `nest auth
  status`, `nest logout`; sessions scoped to the sign-in origin, with the hosted
  sign-in as the default origin.
- **Projects and Project selection** (#88, #93, #103): the
  `ListEligibleProjects` RPC, automatic selection when exactly one Project is
  eligible, a remembered interactive choice when there are several,
  `nest projects list | current | select`, and `NEST_PROJECT_ID` for scripts and
  CI. A login with several eligible Projects never picks one automatically.
- **Hosted SDK profile and connection settings** (#69, #88, #92): explicit
  connection settings, and refusal of settings that conflict instead of guessing.
  The hosted profile default stays off (`HOSTED_PROFILE_DEFAULT = False`).
- **Remote execution**: `cpu=` is passed to the worker, script arguments are passed
  to `SubmitJob` (#23), GPU passthrough follows Slurm's allocation (#76), and
  remote application failures are recorded separately from Slurm completion
  (#102).

### Console

- Management Console MVP (#85), redesigned in #93: members, invitations,
  *Connect to Project*, and Provider approvals backed by the privileged
  management API (#82).

### Controller, authorization and registry

- **Authorization** (#18, #22, #34, #38, #44, #50, #53, #56): identity and
  membership, one-time Platform admin bootstrap, Project-to-Platform eligibility,
  database-enforced execution lifecycle, centralized Project roles and audit
  history, authenticated execution RPCs with a security audit log, Platform
  authorization on Platform-bound RPCs, and persisted Platform-role boundaries.
- **PostgreSQL database and migrations** (#14, #15, #57, #59): one migration
  chain, `nest-db upgrade | status | verify`, an optional local database Compose
  profile, and backup and restore guidance. Email invitations and Invite Links
  (#40) use the optional SMTP outbox (#17).
- **Configuration and reliability** (#12, #13, #16): environment-first
  configuration with Provider bootstrap, CPU forwarding and timeout
  classification, no resubmission of an ambiguous `sbatch`, and bounded gRPC
  status details.
- **Execution Registry and admission** (#87, #102, #105): idempotent attempts,
  admission limits and reservations, trusted-pilot admission controls,
  server-enforced execution authority and verified HPC account bindings, and
  worker protocol 2 outcome records.
- **Workload identity** (#106): scoped CI identities through the GitHub Actions
  OIDC exchange.
- **Slurm core** (#104): a transport-independent Slurm execution core.

### Deployment and operations

- The Controller is configured entirely from environment variables (#61).
- The HPC runtime image includes Git for uv Git dependencies (#63) and is
  published to GHCR as immutable `sha-` and version tags (#81).
- Deployment preflight and `migrate` recovery, and a version-aware Traefik route
  (#92).
- **Hosted staging gateway** (#83, #87, #88, #110): the public gRPC gateway pilot
  with public API security controls, and a gateway that dials the Controller by a
  `grpc-origin`-only name. This remains an operator-run staging pilot.

### Documentation

- A four-step user Quickstart, separate user and operator navigation, a release
  status page and a release checklist (#113). The Quickstart now states that a
  CPU-only call sees no GPU but, with the default worker script, still holds one.

## Breaking and migration-sensitive changes

- **An authenticated Controller requires a session.** SDKs from earlier tags are
  refused (see above).
- **The Controller requires PostgreSQL and schema `0021`.** Run `nest-db upgrade`
  with the new image before starting it. Nest has no down-migrations: roll back by
  restoring the backup taken before the upgrade and deploying the older version.
- **Worker protocol 2.** Update each Platform's Nest checkout (`scripts/worker.sbatch`
  and the worker) before or together with the Controller, or set
  `NEST_LEGACY_WORKERS=allow` only for the rollout. Do not leave legacy workers
  allowed for normal acceptance.
- **Explicit connection settings.** The SDK refuses conflicting settings (for
  example a CA file together with `NEST_CONTROLLER_TLS=false`). Users switching
  between connections clear them as in the Quickstart.

## Operator upgrade path

Follow [Preflight and recover a Dokploy deployment](https://docs.cerulean.works/nest/v0.1.0a5/guide/deployment-recovery)
and the [release checklist](https://docs.cerulean.works/nest/v0.1.0a5/guide/releasing):

1. Drain or wait for running attempts; back up the database.
2. Update each Platform's `NEST_SLURM_WORKDIR/project` checkout (worker script and
   worker, protocol 2) and the HPC runtime image, pulled by digest.
3. Run `nest-db upgrade` with the new image; check `nest-db status` reports `0021`
   with nothing pending.
4. Deploy the Controller (on the Dokploy deployment that follows tags, the tag push
   itself starts this). Confirm the deployed checkout SHA, Controller health and
   migration success.
5. Do not delete persistent volumes. Do not enable the hosted profile default,
   change DNS or open the public gateway as part of this release.
